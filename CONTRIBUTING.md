# Соглашения по разработке

Проект использует Java 21, Spring Boot 4 и Maven Wrapper. Правила ниже описывают **принятый ориентир**, а не утверждают, что весь существующий код уже приведён к нему или что в CI включены все проверки стиля.

## Код и архитектура

- Имена Java-классов, методов, переменных, публичных API и сообщения об ошибках — на английском; README и пользовательская документация — на русском.
- Следуем `.editorconfig`: UTF-8, LF, четыре пробела в Java/XML, два — в YAML, перевод строки в конце файла.
- Контроллер обрабатывает HTTP и валидацию; бизнес-логика остаётся в сервисах, доступ к данным — в репозиториях.
- Внешние контракты описываем DTO, не возвращаем JPA-сущности напрямую. Используем осмысленные имена, небольшие методы и внедрение зависимостей через конструктор.
- Транзакции записи оформляем на уровне сервиса; побочные эффекты (Kafka, Redis) должны учитывать успешность коммита.
- Комментарии — **только там, где требуется объяснить причину или неочевидное решение**, а не пересказать код. Документация публичных контрактов допустима, когда приносит пользу.
- Не добавляем в Git реальные пароли, токены, `.env`, результаты сборки и настройки IDE. Конфигурация для локального запуска не считается production-конфигурацией.
- Любые изменения схемы данных делаем через новую миграцию Liquibase, а не переписываем применённые changeset.
- Для новых исправлений добавляем тест, подтверждающий регрессию; меняя Kafka-событие, учитываем API и consumer.

## Коммиты

Используем [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):

```text
feat(tasks): add task due date
fix(cache): invalidate task views after category update
refactor(api): extract task validation
test(kafka): cover event deserialization
docs: clarify local setup
ci: run smoke test on push
chore: update development configuration
```

Основные типы: `feat`, `fix`, `refactor`, `test`, `docs`, `ci`, `build`, `style`, `chore`. Отдельный коммит — отдельное осмысленное изменение. Не фальсифицируем даты и историю разработки.

## Перед отправкой изменений

1. Проверьте, что новая логика не нарушает контракт API и Kafka.
2. Выполните тесты соответствующего сервиса: `./mvnw clean test` (Linux/macOS) или `.\mvnw.cmd clean test` (Windows).
3. При изменениях инфраструктуры или интеграции проверьте [full-stack smoke test](https://github.com/KULICHx/task-manager/actions/workflows/smoke.yml).
4. Убедитесь, что не появились секреты, лишние зависимости, отладочные сообщения и неиспользуемые файлы.
5. Обновите README, если изменились способы запуска или внешнее поведение.
