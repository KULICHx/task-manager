# AGENTS.md — правила работы AI-агента с проектом

Этот файл описывает рабочий процесс для ChatGPT, Codex и других AI-агентов, которые читают инструкции из репозитория. Применяется ко всем задачам в проекте. Если пользователь задаёт дополнительные требования, учитывай их вместе с этими правилами.

## 1. Главный принцип: небольшие законченные изменения

**Запрещено разрабатывать целое приложение или крупную функциональность одним огромным коммитом.**

- Разбивай объёмную задачу на независимые, проверяемые этапы до начала реализации.
- Один коммит = одно логически законченное изменение: функция, исправление, рефакторинг, тесты или документация.
- Разделяй несвязанные изменения. Не объединяй новую функциональность, косметические правки и переработку архитектуры в один коммит.
- Не создавай искусственные коммиты ради количества: если исправление маленькое и связное, достаточно одного.
- Если пользователь просит «сделать всё», это **не** разрешение залить весь результат одним коммитом.
- Для нового проекта предпочтительная последовательность: инфраструктура/скелет → базовые компоненты → функции по одной → тесты/полировка → документация. После каждого этапа проект должен оставаться в рабочем состоянии.
- Не переписывай историю Git ради красоты. Не меняй даты старых коммитов.

## 2. До изменений

1. Изучи текущие файлы, README, зависимости, архитектуру, существующие тесты и CI.
2. Проверь актуальную ветку, последний коммит и незакоммиченные изменения, если есть доступ к Git.
3. Не предполагая стек заранее, определи его по исходникам проекта.
4. Сформулируй короткий план с этапами и ожидаемыми коммитами.
5. Если пользователь прямо попросил **сначала показать план**, не начинай реализацию до его согласования.
6. Не удаляй и не перезаписывай пользовательские изменения, даже если они кажутся лишними.
7. Не начинай массовый рефакторинг одновременно с реализацией новой функции.

Если нет доступа к локальной файловой системе, работай через подключённый репозиторий, когда он доступен. **Не утверждай, что проверил локальные файлы или запускал код, если этого не было.**

## 3. Реализация по этапам

Для каждого этапа:

1. Сделай минимальный необходимый набор изменений.
2. Добавь или обнови тесты, если меняется поведение.
3. Проверь сборку, тесты и линтер доступными инструментами.
4. Создай **отдельный** коммит с понятным сообщением.
5. После публикации изменений проверь CI (если настроен).
6. Исправь обнаруженную проблему отдельным коммитом `fix(...)`, не скрывая её.
7. Кратко сообщи: что сделано, какие файлы затронуты, SHA коммита, результаты проверок и следующий этап.

Не выдавай непроверенный результат за готовый. Если проверка невозможна, прямо укажи, что осталось неподтверждённым.

## 4. Формат коммитов — Conventional Commits

Используй форму `type(scope): short description`. Сообщения коммитов — на английском.

| Тип | Когда использовать |
| --- | --- |
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `refactor` | Изменение структуры без изменения поведения |
| `test` | Добавление и исправление тестов |
| `docs` | README, инструкции, документация |
| `style` | Только форматирование |
| `perf` | Оптимизация производительности |
| `build` | Сборка и зависимости |
| `ci` | Автоматизация сборки и проверок |
| `chore` | Техническое обслуживание без изменения поведения |

Примеры последовательности коммитов **для нового сайта**:

```text
chore: initialize application structure
feat(layout): add navigation and page shell
feat(home): build landing page sections
feat(tasks): implement task creation
feat(tasks): implement task editing and completion
fix(ui): correct mobile navigation overflow
test(tasks): cover task interactions
docs: add setup and deployment instructions
```

Примеры **для backend**:

```text
feat(tasks): add search endpoint
test(tasks): cover search filters
fix(kafka): handle invalid event payloads
refactor(api): simplify task mapping
docs: document Kafka event contract
```

Это **примеры**, а не требование создавать именно столько коммитов. Коммиты должны соответствовать фактически выполненной работе. Не называй коммит `feat`, если изменил только документацию.

## 5. Требования к качеству

- Сохраняй текущую архитектуру и стиль проекта, если нет обоснования их менять.
- Не добавляй зависимости, фреймворки или сложные абстракции без необходимости.
- Следуй принципам SRP, DRY и KISS без фанатизма: читаемость важнее «идеальной» архитектуры.
- Не оставляй мёртвый код, временные заглушки, бесполезные комментарии и отладочный вывод.
- Не форматируй файлы, не связанные с текущей задачей.
- Названия переменных, методов, классов и комментарии в исходном коде — на английском; пользовательскую документацию и README по умолчанию пиши на русском.
- Комментарий должен объяснять **почему** принято решение, а не пересказывать очевидную строку.
- При изменении публичного API, схем БД или формата события учитывай совместимость и тесты.
- При UI-разработке проверяй адаптивность, доступность, читаемость и единообразие компонентов.

## 6. Проверки и критерии готовности

Этап считается завершённым, когда:

- запрошенное поведение реализовано;
- соответствующие тесты и сборка проходят, **или** их непрохождение честно задокументировано;
- новые изменения не ломают прежний функционал;
- необходимые инструкции и примеры обновлены;
- коммит отражает именно этот этап;
- пользователю известны результат и оставшиеся ограничения.

Для проекта с GitHub Actions проверяй статусы workflows после публикации. Если CI красный, не называй ветку готовой.

## 7. Git и безопасность изменений

- Работай в существующей ветке или отдельной feature-ветке в соответствии с задачей.
- Не используй `git push --force`, `git reset --hard`, удаление веток/репозитория и массовую перезапись файлов без явного согласования.
- Не изменяй старую историю коммитов, авторов и даты.
- Не коммить `.env`, ключи, пароли, токены, дампы БД, логи и артефакты сборки.
- Не выполняй развёртывание в production и внешние необратимые действия без разрешения.
- По возможности сохраняй рабочий репозиторий собираемым после каждого коммита.

## 8. Общение с пользователем

- Пиши прямо, кратко и по делу, на русском.
- Не соглашайся автоматически: отмечай технические ошибки и необоснованные решения.
- Не проси повторно информацию, уже предоставленную в диалоге или репозитории.
- Если задача большая, показывай этапы и фактический прогресс, а не обещай закончить позже.
- Не утверждай, что что-то закоммичено, протестировано или опубликовано, пока не получил подтверждение инструмента.
- Не превращай каждую правку в обсуждение ради обсуждения: выполняй согласованный план последовательно.
- Предлагай изменения исходя из целей проекта, а не ради добавления модных технологий.

## 9. Приоритет этих правил

Этот файл — **инструкции внутри репозитория**, а не глобальная настройка ChatGPT. Агент должен прочитать его перед работой с проектом. Требования пользователя к конкретной задаче и более приоритетные системные ограничения остаются в силе.

Если копируешь файл в другой проект, проверь, что правила соответствуют его стеку и рабочему процессу.
